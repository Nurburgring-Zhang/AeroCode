# Graph Engineering：把任务变成有依赖关系的 DAG

Graph 层只回答一个问题：**哪些工作是节点，它们之间的依赖是什么？** 空间维度（结构）由本层负责，时间维度（继续/停止）交给 `loop-engineering`。

`[软约束]` 本文档是纪律；`[硬约束]` 是 `scripts/gate_state_validate.py` 对节点契约的校验退出码。

## 1. 三条铁律

1. **边 = 数据依赖，不是时间顺序。** 「B 用到 A 的产出」才连边；「我习惯先做 A」不连边。凡是没有连边的节点，默认必须并行。
2. **确定性工作不调模型。** 能用命令/脚本/正则/文件操作完成的节点标 `deterministic=true`，此类节点**禁止调用模型**。这是最大的一笔省钱项。
3. **拆分的目的是让单步变轻，不是让步数变多。** 反面实测：某模型把一个网页生成任务拆成 75 step / 124 次请求，仍烧掉 11,533,959 token，因为每步依然很重且带全量上文；对照模型 8 step / 15 请求即完成。**拆分必须同时降低单步上下文体积，否则是负优化。**

## 2. 节点契约（Node Contract）

每个节点必须写全六字段，缺一即视为未规划：

```json
{
  "id": "n3",
  "goal": "一句话，单一产出",
  "inputs": ["n1.outputs.schema_path", "docs/spec.md"],
  "outputs": ["src/parser.py"],
  "acceptance": [{"kind": "cmd", "value": "pytest tests/test_parser.py -q", "expect_exit": 0}],
  "deterministic": false,
  "owner": "builder-A",
  "verifier": "verifier-B"
}
```

- `goal`：一个产出。出现「并」「同时」「以及」通常意味着该拆成两个节点。
- `inputs`：只能是**上游节点的具体输出字段或明确文件路径**。禁止写「上文」「之前的讨论」「相关背景」——这类写法就是上下文回灌的入口。
- `acceptance`：`kind ∈ {cmd, file, assert}`，必须可机检（详见 `loop-engineering` 第 2 节）。
- `deterministic=true` → 必须给出确切命令，且不得出现模型调用。
- `owner != verifier`，硬约束，禁止自评签字。

## 3. 拆分方法（怎么切出节点）

按序尝试，先命中即用：

| 切法 | 适用 | 例 |
| --- | --- | --- |
| 按产出物切 | 交付物明确 | 每个文件/每个接口/每个报告章节一个节点 |
| 按数据依赖切 | 有明显管道 | 采集 → 清洗 → 计算 → 呈现 |
| 按能力域切 | 需要不同专长 | 后端 / 前端 / 测试 / 文档 / 安全 |
| 按风险切 | 有不可逆动作 | 把不可逆步骤单独成节点并前置审批门 |

单节点体检（四问全过才算合格）：

1. 产出是**一个**且可被机检？
2. 15~30 分钟能完成？
3. 只依赖显式列出的 inputs，不需要「知道整个任务的来龙去脉」？
4. 失败时影响面局限在本节点？

任一不过 → 继续拆；拆完后**必须回看铁律 3**，确认单步上下文确实变轻了。

## 4. 结构模式

| 模式 | 用法 | 要点 |
| --- | --- | --- |
| fan-out 并行扇出 | 无依赖节点同时派发 | 派发前先声明汇聚点，否则产出无法合并 |
| fan-in / barrier 汇聚 | 多节点产出合并 | 汇聚节点必须先校验每个上游 `outputs` 真实存在（真实 FS 读回），缺一即 BLOCK，不许「先合了再说」 |
| 条件路由 | 分支取决于运行结果 | 路由条件必须是可读取的具体值（退出码/字段值），禁止「看情况」 |
| 审批检查点 | 不可逆动作前 | 停下来问主人，得到明确批准再走，批准记入状态文件 |
| 专家会战 | 单节点连续卡住 | 空闲 owner 转为并行探路（不同方案，非同法重试），命中一个即收束 |

**并行的前提是隔离**：并行节点不得写同一文件、不得依赖彼此的中间态；否则改为串行或引入合并节点。

**汇聚语义必须显式声明（v1.1，机检）**：`barriers[].policy` 四选一，不许「看情况」：

| policy | 语义 | 约束 |
| --- | --- | --- |
| `all_success` | 全部成功才放行 | 默认最严 |
| `min_success` | 至少 N 个成功即放行 | 必须写 `min_count` 且 1 ≤ min_count ≤ len(waits_for)，超出等待分支数直接 BLOCK |
| `timeout_degrade` | 超时降级放行 | 降级事实必须留痕 |
| `critical_fail_stop` | 关键分支失败即全停 | 关键分支要在 waits_for 中可识别 |

不写 policy 的汇聚是隐式 all_success，一旦有人以为「超时也能过」，故障就变成误会。

## 5. 子代理上下文隔离（省 token 的关键）

派发子代理时，只给三样：

1. 本节点契约（goal / inputs / outputs / acceptance）
2. inputs 指向的**具体内容或文件路径**
3. 必要的全局纪律指针（技能名，不是技能全文）

**不给**：完整对话历史、其他节点的中间推理、无关背景。子代理返回时也只回三样：产出路径、验证证据、未解决缺口（≤1000 字）。

理由：输入 token 是成本主项（实测某案例输入占总 token 98%）。上下文隔离是唯一能从结构上压掉这部分的手段。

## 6. 模型分层（把活分给最便宜的执行者）

| 工作性质 | 交给 | 例 |
| --- | --- | --- |
| 确定性、可枚举、可脚本化 | 代码/命令，**零模型调用** | 批量改名、格式化、行数统计、schema 校验、grep 统计、hash 比对 |
| 需理解但结构固定 | 一次模型调用 + 模板 | 提取字段、按模板生成、翻译 |
| 需判断与权衡 | 模型 + 独立验证者 | 方案选型、代码审查、事实校验 |
| 高风险不可逆 | 模型多候选 + `self-verify-scaling` + 人工批准 | 迁移、删除、部署 |

自查：如果一个节点的动作可以写成一行命令，就**不许**让模型逐条手工做。

v1.1 起上图必登记（T3，`gate_state_validate.py` 机检）：`calls_model=true` 的节点必须写 `model_tier ∈ {cheap, standard, heavy}`。档位只登记不评判——这是计量字段，让「贵模型干杂活」的浪费可见，不拦你用强模型；不上图、不登记，这笔账永远糊涂（阈值见 `spec/thresholds.json` 的 `model_tier` 节）。

## 7. 边上验证门

验证挂在**边**上而不是节点内部：上游产出流向下游前必须过门。

```
n1 ──[gate: file 存在 && schema 校验通过]──> n2
n2 ──[gate: pytest 退出码 0]──────────────> n3
n3 ──[gate: 独立 verifier 签字 + 真实性扫描]─> 交付
```

优先用**确定性验证**（类型检查、单测、schema 校验、退出码），只有在确定性手段无法覆盖时才用模型判定。能机检的一律不用模型判定。

v1.1 起边门是硬契约（`gate_state_validate.py` 机检）：

1. **`kind=cmd` 的门必须写 `expect_exit`**（默认 0）。没有期望退出码的命令验证无法判成败，等于没有验证。
2. **T3 图至少挂一条边门**（阈值见 `spec.edge_gates`）：高风险图一条边门都没有，验证就形同虚设——schema 只能保证边门形状合法，不能保证图里真的用了门。

## 8. DAG 登记（写入状态文件）

```json
{
  "contract_version": "1.1.0",
  "graph": {
    "nodes": [ /* 节点契约数组 */ ],
    "edges": [{"from": "n1", "to": "n2", "gate": {"kind": "file", "value": "out/schema.json"}}],
    "parallel_groups": [["n2", "n3", "n4"]],
    "barriers": [{"at": "n5", "waits_for": ["n2", "n3", "n4"], "policy": "all_success"}]
  },
  "artifacts": [
    {"id": "parser-impl", "produced_by": "n2", "supersedes": "parser-impl-v0"}
  ]
}
```

校验：`gate_state_validate.py` 检查环、孤立节点、未声明 inputs 来源、`owner == verifier`、`deterministic=true` 却声明了模型调用；v1.1 起还检查边门 `expect_exit`、T3 边门覆盖、barriers `policy`/`min_count` 语义、`contract_version` 格式（向后兼容：旧版本照常过，版本高于已知只告警），以及 T3 的工件登记：

- **工件登记（T3，`spec.artifacts`）**：交付物登记为 `artifacts[{id, produced_by, supersedes}]`，`produced_by` 必须指向真实 graph 节点（transcript 不是数据库，产出必须溯源到生产节点）；`supersedes` 构成最小版本谱系（ADR 同构），不得断链（指向不存在的工件）或成环。
- **契约版本**：状态文件顶层写 `contract_version`（`^[0-9]+\.[0-9]+\.[0-9]+$`，阈值见 `spec.contract`）。规矩改了系统立刻知道新旧关系，而不是报一堆莫名字段错误。

## 9. 常见反模式

- 把「先想清楚再做」写成节点（不是工作单元，没有可机检产出）。
- 边表达时间顺序 → 全图串行 → 白等。
- 节点 inputs 写「参考上文」→ 上下文回灌 → token 爆炸。
- 汇聚时不校验上游产出真实存在，凭工具回执就往下走。
- 为了「看起来规划得细」而拆出几十个仍然很重的节点（拆得多不等于拆得好）。
- 验收命令只验「没改坏」不验「真的交付了」（交白卷盲区，见 `loop-engineering` 第 2 节与 `reference-gates.md` G4）。
